# KVM screen: failure modes

What goes wrong in the UI layer, which the engine's own FAILURE_MODES.md files do not cover.
The engine decides (gestures, keys, video, view maths); this layer wires and draws it, so its
bugs are about ownership and timing.

Tests beside the code assert each mode as something a person or the target would observe, never
source text. The end-to-end run (`apps/web/e2e/kvm.e2e.mjs`) covers the same ground against a real
host and the fake kvmd.

## Focus and the soft keyboard

- K1. A tap on any dock button must leave focus on the hidden field, or the system keyboard drops every time a key is used. The press is held off at pointerdown (touch and pen) and at the compatibility mousedown that follows it, and `refocus` gives focus back only if the keyboard was wanted.
- K2. A blur right after a dock tap is that tap passing through, not the user putting the keyboard away; one with no tap in front of it is. Reading focus instead of intent reopened a keyboard the user had just closed.
- K3. The hidden field is uncontrolled. Re-rendering the screen (a toast, a state change) must never reset its value or its caret, or the soft-keyboard diff replays what was already typed.
- K4. Opening the ⋯ sheet puts the keyboard away (the sheet needs the room) and nothing reopens it; closing the sheet by an outside press or Escape leaves the keyboard down.
- K5. A dialog owns the keyboard: what is typed into it must not reach the target, and opening one lets go of every modifier the target is holding.

## Keys

- K6. A modifier tapped on screen is armed (announced as pressed), tapped again quickly is locked (still announced, plus a mark colour alone cannot give), tapped once more is off. The next key consumes an armed one and keeps a locked one.
- K7. The Caps key shows the TARGET's LED, not the last tap: it is `aria-pressed` from the Pi's report, and says so in its title when the Pi has not reported.
- K8. Fn and More are one block at a time. Opening one closes the other, and they never both push the dock past three rows.
- K9. A shortcut key (Ctrl+C, Alt+Tab) goes out as one chord through the engine's queue, with any armed modifier folded in once.

- K21. While the HID socket is down every key in the rows is disabled: a press then goes nowhere, and the offline queue drops anything that old, so offering the key is a promise nobody keeps.

## The sheet and the toolbar

- K10. Touch input and trackpad mouse are stored in this browser under the console's own keys; the second is offered only for the trackpad on a Pi that has a relative output, and shows pending while the Pi has not reported the mode asked for.
- K11. A pinned macro can be started only when nothing else is typing and, for a macro with key steps, the HID socket is open. The button is disabled from the same facts the runner refuses on, so the refusal is visible before the press.
- K12. Speaker and mic exist only while WebRTC carries the picture (MJPEG has no audio). The pressed state follows the audio state, and a failed mic says why on the button.
- K13. The zoom-out button exists only while zoomed in, and pressing it restores the whole picture and hides itself.
- K14. A menu closes on a pick, an outside press and Escape; Escape closes one layer only and returns focus to the button when it was inside.

## Toast and dialogs

- K15. A failure interrupts a screen reader and stays longer than a confirmation; a sticky notice stays until replaced; the text is emptied only after the fade, and not if something newer arrived meanwhile.
- K16. `openDialog(name)` renders whatever is registered under the name; the last registration wins; a name with nothing real behind it still opens a labelled dialog that closes on Escape.
- K17. Paste: nothing to send is not sendable; Ctrl+Enter sends; the dialog closes at once (the paste takes minutes) and the engine's paster refuses while a macro runs.

## Picture, lens and OCR

- K18. The view transform reaches the image, the video and the held frame together, and the zoom state published to the UI is the machine's, not a copy.
- K19. A region picked for OCR is in the picture's own pixels whatever the letterbox or zoom, clipped to the picture, and a tap, a miss or Escape resolve to nothing.
- K20. The link lifecycle is bound once per session: a long stay in the background kicks the socket exactly once, not once per mounted screen.

## Behind another tab

The screen stays mounted for the whole visit (see `app/panes.tsx`), so "mounted" no longer means "in use". `useKvmActive()` says whether it is the tab in front.

- K22. The picture, its stream and the link are never torn down by a tab change: the same `<img>`, the same source, no new socket or stream request, live on return.
- K23. Nothing typed on another tab reaches the target: the hidden field refuses keys, the desktop app's window-level forwarding and host-paste shortcut are off, and the pane is `inert` so no pointer or focus reaches it.
- K24. Changing tab lets go of what the target holds (modifiers) and puts the soft keyboard away, once, from the change itself; the handlers stay bound for the return.
- K25. The pointer machine treats "another tab is in front" like "a dialog is open" (no gestures, no cursor), and a real dialog stays open across the change. No cursor report goes to the agent while hidden.
- K26. The screen wake lock and the document-level handlers (Escape and outside press for menus, the OCR picker's Escape, the Safari pinch guard) follow the tab being in front, not the screen being mounted.

## The shared cursor

- K30. The stream names this page: updates carrying this page's own client id are its own moves coming back, and are never drawn as somebody else's.
- K31. Each update is delivered once and in order (a repeat or a straggler is dropped); a message that is not an update is ignored and the next one still arrives.
- K32. A host that restarted starts its sequence again: after a stream error the next update is taken whatever its number.
- K33. A listener that comes late (the KVM tab mounting after the stream opened) is told the newest position at once; one that leaves while it is being told does not stop the others.
- K34. A hidden page holds no stream and takes a fresh one, which begins with the current position, when it is shown.
- K35. The page's input socket URL carries its client id, so the host can say whose moves are whose.
- K36. The picture draws what it is told: the trackpad blob moves with the cursor, or (mouse, direct touch, a relative trackpad) a distinct marker for somebody else's pointer; the same point of the picture after a resize.
- K37. A page that is moving the pointer is not moved by another client, and nothing it is told is ever sent to the target.

## Audio on a phone

- K38. The picture starts muted, and Safari refuses to unmute it unless the attempt runs inside a real user gesture. A touch counts as one when it is released (`pointerup`, `touchend`, `click`), not when it lands (`pointerdown`), so waiting for the first touch to LAND left an iPhone silent however often it was tapped. The unmute is tried on the first release of a touch, a click or a key press, once, and the waiting stops the moment it has run or is cancelled.
- K39. The camera goes to the target as `capture` on the video track and `cam: true` in the Janus `watch`, and only when the Pi's `features` reply says `cam` (PiKVM V3/V4 with `ucamera` and `otg/devices/camera/enabled`). Without that feature the camera button is drawn but disabled with the reason (K53), because a camera the Pi cannot honour would be turned on and go nowhere. The camera is chosen where the microphone and speaker are, remembered under `pikvm-console-camera-device`, and pinned with `exact` like the microphone, so an unplugged camera is named ("Camera gone") and never replaced by another; changing the choice while the camera is on restarts the session. The permission prompt is raised first and its tracks are dropped, so a refusal reads "Denied" and a missing device "No camera". The target decides when the stream starts; turning the camera on only allows it. The exchange with a real Pi needs a PiKVM with `ucamera`; the camera control end to end is run against a fake Janus (`~/.cache/pikvm-e2e/webcam-control/`).

## Recording the session

The HOST makes the recording (it joins the PiKVM's own stream; `src/server/recordings/capture/`, `host-recorder.ts`): the page starts and stops it, shows its state, and sends the person's microphone. Code: `recorder/` (recorder.ts the control, live.ts the host's live state, mic.ts the microphone, api.ts). The Recordings page is `../recordings/` (its failure modes are K58 onwards, and K74 to K83 for what the host's recorder added). The wire protocol is `packages/contracts/src/recordings.ts`. Proof: `~/.cache/pikvm-e2e/host-recording/e2e.mjs`. The numbers K40 to K49 belonged to the browser's own recorder (MediaRecorder, chunk uploads) and were removed with it; they are not reused.

- K50. A recording an older version took from a browser's MediaRecorder is a file with no length, and a `<video>` will not seek in one (a recording the host made has its length). The player asks for a time far past the end once, which makes it read to the end and learn the length, and puts the position back at 0; transcript lines seek from then on.
- K51. The Recordings page reads the list when it opens and each time it comes to the front, and then only polls (every 3 s) while a recording is being made or transcribed, and stops by itself. A poll that fails keeps the list on screen and says it is stale; a first load that fails shows the error, not an empty list. Delete asks first, with Cancel focused.
- K52. A host that cannot transcribe (no models, no ffmpeg) is said so on the page with its reason; there is no Transcribe button, and playing, searching titles and deleting still work.

## The camera control

Code: `camera.ts` (presets, per-camera prefs, the view every placement reads), `camera-control.tsx` (toggle, menu, sheet row), `camera-panel.tsx` (preview and options), `camera-preview.ts` (the self-view's lifecycle), `janus-stream.ts` (what is sent), `picture-controller.ts` (state, unplug and permission handling).

- K53. The camera control is always drawn, in the toolbar (toggle and arrow), the dock and the sheet, whatever the Pi says, because a button that appears only on a PiKVM V3/V4 with `ucamera` looks to everyone else like a missing feature. When the camera cannot be turned on it is `aria-disabled` (not `disabled`, so a tap still lands and a phone is told why) and its title, pip and the menu's note give the reason, in this order: the page is not secure ("Needs HTTPS": there is no `mediaDevices`), the Pi's `features` reply has no `cam` ("Unavailable on this PiKVM": it needs a V3 or V4 with the `ucamera` package and the OTG camera enabled, with links to the PiKVM handbook and the README), no WebRTC session has answered yet, so the picture is MJPEG or the Pi has not been asked ("Needs WebRTC"; once a session has answered, a restart of the session, which every camera change causes, never blocks the button). A press on a disabled camera sends nothing and says the reason in a notice. The `features` check stays the gate for sending: nothing is captured or offered to a Pi that did not say `cam`, a camera left on from an earlier session is turned off when a new session reports no `cam`, and a camera that is already on can always be turned off. The menu and its preview work in every one of these states, so someone can see their camera before it can be sent anywhere.
- K54. The self-view exists only while the camera menu (or the sheet's unfolded options) is on screen: `getUserMedia` on mount, every track stopped on unmount or when the camera or quality choice changes, and a capture that resolves after the menu closed is stopped as it arrives. It is never opened when the browser lists no camera, or the camera chosen by name is not in the list (asking would raise a permission prompt for nothing); it says so instead. A refusal ("Camera access was refused"), another app holding the camera ("In use"), a missing device, a page that cannot open a camera and any other failure each have their own sentence on the preview and, where asking again can help, a "Try again". Camera names stay empty until a camera has been allowed once, so the list is read again as soon as the preview opens.
- K55. What is sent is a quality preset, a size (360p, 480p or 720p) and a frame rate (30 or 15 fps); 720p at 30 fps is the default, remembered for each camera under `pikvm-console-camera-prefs` with its mirror choice. Nothing above 1280x720 is offered: the PiKVM handbook gives that as the most the USB camera takes (640x480 in its safe mode), and the `features` reply is only a yes or no, so there is no larger limit to read from it. The size and rate are `ideal`, so a camera without the mode gives its nearest, and the menu shows what the browser really opened (the preview's chip, and "Asked for ... ; this camera opened at ..." when they differ) and what the session is ready to send (the track's own settings, read after the answer is made). Mirroring is the preview only: the target always sees the true picture. A changed preset restarts a live camera, the same as a changed device.
- K56. A camera that is on and then goes away is turned off with the reason, not left "sending" a dead track. The session watches the camera track's `ended` event (unplugged, or permission withdrawn) and the page watches `devicechange`; the reason is read, in order, from the Permissions API ("Denied": allow it in the browser's site settings), then the device list ("Camera gone" when a camera chosen by name is missing, "No camera" when none is left), else "Stopped". Turning the camera on again is left to the person: a camera that comes back (or a permission that is allowed again, which the page sees through the permission status `change` event, since it raises no `devicechange`) clears "Camera gone", "No camera" or "Denied" and says so once, but does not switch itself on.
- K57. A session made after a drop (the page came back, the network returned) carries the camera again: it is created wanting what the camera button says, not off. Without that the button said On while nothing was sent.
- K73. Chromium lists no camera at all while the camera permission is blocked, so an empty list can mean two faults. The page reads the Permissions API first: blocked is "Denied" (a warning, not a block: a press asks again, which is how a fixed setting is noticed, and the preview says "Camera access was refused" with Try again), and only an empty list with the permission not blocked is "No camera" (disabled, with the reason, before anything is pressed). A failed press is always shown as a notice as well as a pip, because on a phone nobody hovers a title.

## The Recordings library and search

Code: `../recordings/` (the page: library-view, search-results, watch-view, menu, poster, find, transcript-export) and, on the host, `src/server/recordings/search-index.ts`. The wire protocol is `packages/contracts/src/recordings.ts`. Proof: `~/.cache/pikvm-e2e/recordings-library/e2e.mjs`.

- K58. The search index is a copy, never the truth. It is made again at start when it is missing, of another `user_version`, not a database, or older than a transcript: each recording's `transcript.json` modification time and size are kept in the index and compared, a changed or never-indexed transcript is read again, and rows of recordings that are no longer on disk are dropped. A rebuilt index answers every query exactly as the kept one did.
- K59. A host that cannot open the index (no FTS5, a directory where `index.db` should be, a read-only disk) still starts: recording, playing, renaming and deleting work, `GET /search` is 503 with the reason, and the page says "The search could not be made" with that reason and still lists. Failing to remove a bad `index.db` must not stop the host starting.
- K60. What a person types is only words. Every word is quoted before it reaches FTS5, so `OR`, `NEAR(`, `col:x`, `*`, quotes, parentheses, SQL and control characters are words or nothing, never an operator or a 5xx. Empty, white space, nothing but punctuation, more than 200 characters, a limit outside 1 to 100, a negative offset, a bad date and a speaker over 100 characters are 400 with a sentence. Only the last word is a prefix, and only when the text does not end in a space or a quote, so "monit " does not find "monitoring" but "monit" does.
- K61. A snippet is plain text and ranges, never HTML. The page wraps the ranges in `<mark>` elements it makes itself, and a title or a transcript that says `<img onerror=...>` is drawn as those characters. The marker characters used to find the matches (U+0001, U+0002) are replaced by spaces in anything indexed. Ranges of words separated only by white space (a phrase) are one range, and a long segment is cut around the first match with an ellipsis and ranges that still point at the right words.
- K62. A recording's rows leave the index when it is deleted (one at a time, in bulk, by retention), and its segments leave when it is transcribed again, so a search never finds words of a recording that is gone or whose transcript is being replaced. A transcription that finishes after its recording was deleted indexes nothing: the check and the write are one synchronous step.
- K63. A rename is one line of at most 200 characters (runs of white space, tabs and newlines become one space); `null` or empty is the default name ("Recording, <date>"). It is saved in `meta.json` first and then in the index, so a failed index write is logged and the next start fixes it, never a lost title. In the page, Enter and leaving the field save once (not twice), Escape saves nothing, an unchanged name sends nothing, and a refused save puts the old name back and says why.
- K64. The address is the state: `/recordings?q=&filter=&sort=` and `/recordings/<id>?t=&q=`. The router reads `t=95` and `q=2024` as numbers, so every value is read back through `route-state.ts`. A reload, the back button and a pasted link keep the query, the filter, the sort and the second. The page is kept mounted while another tab is in front: it keeps what it showed, pauses its player, reads the list again when it returns and takes no `/` key while away.
- K65. A link that names a second (`?t=21`) lands there, paused, with that line marked, even in a file with no length (K50: the player learns the length first and only then goes to the second). The match shown first is the one at that second, not just the first one in the transcript. A recording that does not exist (deleted, or past retention) says so and offers the way back, rather than a blank player.
- K66. A thumbnail is the first frame, taken in the browser with a hidden video and a canvas: only once the row is near the screen, two at a time, kept in memory (at most 150) and given up when the recording is deleted. A recording that is still being made, empty, failed, or in a codec this browser cannot decode shows a film-strip icon, never a broken image and never a request per redraw.
- K67. Bulk delete asks first with the count, Cancel focused (Escape cancels); the rows it could not delete stay, and the first reason is said; a recording already gone counts as deleted. Rows that leave the list (the sweep, another tab) leave the selection; Shift extends from the last box; the header box is indeterminate for some.
- K68. `/` puts the cursor in the search box only when nothing that takes text has focus, no dialog or menu is open and the page is in front. Escape empties the box, and on an empty box leaves it. A pause of 250 ms, not each key, puts the text in the address; text typed while an earlier settle is still coming back is never overwritten.
- K69. Menus (row, sort, download) are drawn in a layer of their own placed from the button, open upwards when there is no room below, close on Escape (focus back on the button), Tab, an outside press, a scroll and a resize, move with the arrows, Home and End, skip disabled items, and carry `menuitem` or `menuitemradio` roles. Arrow keys move between the row titles; a title is a real link (Enter, middle click).
- K70. On a narrow page (by the width of the page, not the device) a row is a card; nothing overflows sideways at 390 px; on a coarse pointer buttons and chips are 44 px high and a row has no hover-only pencil (Rename is in its menu). Hover styles apply only on a fine hovering pointer. With reduced motion, the live-recording pulse and the loading shimmer stop.
- K71. The line being played follows playback only while "Follow playback" is on; scrolling the transcript by hand, or moving between matches, turns it off, and pressing a line or the toggle turns it on. Moving between matches seeks the player without starting it. Following also starts when play starts far from the visible lines.
- K72. Copy, .txt, .srt and .vtt are made from the segments in the browser: SubRip uses `,` and WebVTT `.` before the milliseconds, a cue is never empty and never holds a blank line, WebVTT text is escaped (`&`, `<`, `>`, `-->`) and the speaker is a voice tag. A clipboard the browser refuses says so instead of "Copied".

## Recording on the host

Code: `../kvm/recorder/` (the control, the live state, the microphone) and `../recordings/` (the library). On the host: `src/server/recordings/host-recorder.ts` and `capture/`. Proof: `~/.cache/pikvm-e2e/host-recording/e2e.mjs`.

- K74. The host records, not the page. Record starts and stops the HOST's recording (`POST /start`, `POST /:id/stop`), so it needs no WebRTC picture (MJPEG is fine: the host joins the Pi's stream itself), it works from any tab, and closing or reloading the page loses nothing but the microphone.
- K75. The button, its clock and the library show the host's state, not what this page did: one server-sent stream (`/live`, held only while the page is shown, as the shared cursor's is: K34). A recording another client or a meeting detector started shows here with the same clock (the host's `elapsedMs` at its `at`, counted on with this page's own clock), and either page can stop it. No state at all (the stream is down) never reads as "ended".
- K76. One recording at a time. A start that meets another recording (409) follows it instead of failing: the page says it now follows the one in progress. A start at the disk limit (507) shows the host's own sentence on the notice and on the button's title, warns, and records nothing; a click after that tries again.
- K77. A recording the host ended and this page did not stop (the total quota, the per-recording cap, a raw backlog the re-encoder could not keep up with, the PiKVM gone for 15 minutes, a host restart) is told in words with "what was captured is kept", once, from the recording's own `reason`. A stop this page asked for says only that the recording was stopped and is being finished. Another client's plain stop says "stopped" without alarm.
- K78. The microphone is optional and never decides whether the recording happens. It is asked for with the pinned device as `exact` (a gone headset is named, never replaced), mono, with echo cancellation and noise suppression. Refused or missing: the recording goes ahead with no microphone track and says so once. A browser with no Opus encoder (no WebCodecs `AudioEncoder` with "opus": Safari before 26, Firefox before 130) is told so before the click, in the button's title, and records without one; nothing is encoded in JavaScript.
- K79. The `AudioContext` is made and resumed inside the click that starts a recording, before any await (a context made after an await may be refused sound), and its worklet's output goes through a gain of zero to the destination, so the target is never heard twice and the worklet still runs.
- K80. Frames, not a stream: 20 ms of Opus each, with the capture time on this page's clock worked from the audio clock and anchored to the wall clock by the lowest arrival delay of the last 10 to 20 s (the offset moves at most 0.25 ms a frame, so a long recording drifts without a jump). A socket that drops is opened again with growing pauses and what was missed is silence on the host; a frame the encoder or the socket cannot take (25 waiting, 64 KB buffered) is dropped, never queued. The encoder numbers what it emits by the samples it was given, one frame after another, whatever gaps the capture had (the worklet's first blocks can be empty, and Chrome's output then matched only the first frame): so frames are handed to it on a gapless 20 ms timeline of their own and each output is matched to its real time by that number.
- K81. The host closing the socket ends the feed with the tracks let go: 1000/1001 (the recording ended or the host is stopping) is silent, 4000 (another page took over the microphone) says so, 4404/4409 (no such recording in progress, or one that takes no microphone) and an encoder or device failure say the microphone is no longer recorded. A microphone unplugged mid-recording is a failure of the feed, not of the recording.
- K82. A page that reloads in the middle of a recording it started with the microphone takes the microphone up again, once per recording, from a marker in `sessionStorage`, if the browser lets it without asking (a page just loaded has had no click, so the audio starts at its first touch or key); if not, it says the microphone stopped at the reload.
- K83. The library tells recordings apart by who made them and how they ended. A recording being captured or finished is not playable (the file does not exist yet: 409 on `/media`), has no thumbnail, no download and no expiry; "Finishing N%" is the re-encode (the bar is indeterminate when the host cannot say). A gap (the PiKVM was out of reach) shows as "N gaps in the picture" with its place, and the button of a client warns "reconnecting" while it lasts; an early end shows its reason. Delete works on a recording in progress (the dialog says it is stopped first). A recording an older version took from a browser says "Uploaded from a browser" and is otherwise the same.
- K84. The host being out of reach is not the recording being over. The capture is on the host, so when the live stream breaks (a stream error, a 502 from the desktop app's forwarder, a half-open socket that goes silent for 8 s while the host should be sending a state every second) the page keeps the LAST state it heard and marks it stale once the break has lasted 3 s (a proxy cutting an idle stream and the page reopening it at once is not worth a warning). The Record button in the toolbar, dock and sheet then stays "recording" but amber and not pulsing, with the time shown as unknown (`--:--`, "Lost contact" in the sheet), `data-stale`, the label "Lost contact with the host: stop recording (last seen at mm:ss)" and the title "Cannot reach the host. The recording may still be running there; it will be shown again when the connection is back."; one notice says so (once per loss). The page opens the stream again itself, with growing pauses (1, 2, 4, 8, then every 15 s), because the browser's own retry stops for good after an HTTP error such as that 502. The first state of the new stream clears the warning, says "Back in contact" if the recording still runs, and if it ended meanwhile the usual end notice (K77) says why. With no recording known before the loss the button stays plain idle and no notice is made: the screen's own status line ("Screen unavailable · input offline") is the page's one notion of an unreachable host, and is reused rather than adding a second. A click while stale is Stop: it asks the host, and if it cannot get through says "Cannot reach the host, so the recording could not be stopped. It may still be running there." (never "stopped"), keeps the microphone feed and its reload marker, and asks the stream again at once. A hidden page holds no stream but keeps saying "lost contact" until it hears the host. Proof: `~/.cache/pikvm-e2e/forward-recording/e2e.mjs` (section `lost`).
- K86. The recording clock starts at the click, not at the host's answer. The page sends how long ago the click was (`clickedAgoMs`) and the host counts the recording from that moment, so the first reading the button shows is the click's and the count never steps back when the host confirms. Until then the button shows the start as pending (`pendingSince`) and counts from the click. The host starts ffmpeg and the Janus handshake with the PiKVM together; a keyframe is asked for only once ffmpeg listens and the stream is up, because a request that arrives early goes nowhere and the gate would wait a whole interval.
- K87. The archive is a second copy, and the host's own file goes only after it is verified. A copy is streamed to `<file>.part`, its size and SHA-256 are read back from the finished file after the rename, and only then is it recorded as `copied`. Retention and the disk limit both wait for a `copied` archive state, so a failed or unverified copy keeps the host's file. A missing archive folder (an unmounted share) is never replaced by a folder on the host's disk: the copy fails with "The archive folder ... is not there." and is tried again later.
- K88. A failed copy is retried with a growing pause (one minute, doubling, capped at six hours), and the reason is kept on the recording's archive state. A file already in the archive under the same name is never overwritten: a different one is left alone and the copy fails with "The archive already holds a different file under this recording's name, so it was left alone." A recording whose file the host has already removed is not copied again.
- K89. Removing a file (retention, or the disk limit once the copy is verified) keeps the recording, its transcript, title and search rows, and marks the view `mediaRemoved` with `mediaExpiresAt` null. `/media` then answers 404, and transcribing again answers 409, because it needs the file. Deleting a recording by hand removes only the host's own directory: an archive copy is never deleted by the host.
- K90. A transcript retention shorter than the file's (`PIKVM_RECORDINGS_TRANSCRIPT_RETENTION_DAYS`) takes the whole recording, file and transcript together, when the transcript's time runs out. When the archive is set and a copy has failed, the library shows "N recordings are not copied to the archive folder yet, so the host keeps their files. The copy is retried." with `role="alert"`, so a dead share is not silent.
- K91. The Nemotron diarizer (`PIKVM_ASR_DIARIZER=nemotron`, off by default) never stops a transcription: if the engine or model is missing, cannot start (a CPU without AVX2, FMA and F16C dies with an illegal instruction, so its exit is not zero), exits with an error, prints output that does not parse, or runs longer than four times the audio (two minutes at least; it is killed with SIGKILL), the worker sends a note with the reason ("Nemotron diarizer unavailable, using sherpa: ...") and diarizes the target with pyannote and ERes2Net instead. Speakers are numbered by first appearance either way. Proof: tests/nemotron-diarizer.test.ts (parsing and the timeout kill) and the hardened-container run of the engine on a two-speaker fixture. Not proved: the arm64 engine, a CPU without AVX2, real meeting audio.
- K92. A drop in the connection is said once, app-wide, by the connection banner (`apps/web/src/app/connection/`), and it names the channel that failed. Four channels are kept apart: the host probe (`GET /app/api/v1/session`, every 5 s visible and 15 s hidden, 4 s time-out, one in flight), the target link (the engine's event socket to the host), the picture stream (the status chip's signal) and the chat socket. A failed probe says only "No answer from the host for m:ss. Reconnecting..."; two in a row are needed, so one failed probe that is followed by a good one shows nothing, and "The host is slow to answer (2.9 s)" needs two probes over 1.5 s. "The host cannot reach the PiKVM." comes only from the target link having been open and now closed for 6 s while the probe answers promptly (never from a probe failure, and not while probes are slow, because a link that cannot reopen over a slow path says nothing about the PiKVM). A picture or chat channel that is down for 6 s while the host answers is named alone ("The picture has been unavailable...", "The chat connection has been down...") and does not mark the whole app lost; "No signal" is the target's and is not a drop. The browser's `offline` event is shown as "This device reports no network" and is cancelled by one answer from the host. The banner holds a state for at least 3 s before it changes and keeps "Connection back after 1 min 04 s" for 4 s, so it does not flap; a toast says the same (the KVM toast and the chat toast, each on its own tab; the chat keeps its own "Connected again" for its own socket). A probe that goes wrong (times out or is slow) is judged by a second channel that is not in the browser's connection queue: the page pings the event socket (kvmd answers with a pong) while the probe waits. A pong within 1.5 s means the host is alive and the probe was held up in the browser (over HTTP/1.1 a browser keeps six connections per host, and a page holds about five streams open, so a second tab or a parked page can starve it): the probe is unknown, neither a failure nor slow, and nothing is shown. A pong that takes longer makes it a slow answer of that length; no pong (socket closed, or silent for 4 s) leaves the probe's own verdict. A hidden tab does not count the downtime of sockets that sleep with it, and a host that has just come back gives the link a fresh 6 s before the PiKVM is blamed. Settings, About, "Recent drops" lists the last 10 (time, length, cause), kept in this tab only (sessionStorage). Proof: the real-browser run (loss, recovery, a blip, slow replies, a stalled picture alone, the PiKVM going away) under `~/.cache/pikvm-e2e/connection-monitor/`, not committed.

## The cached app shell and updates

Written before the worker was changed. The installed app opens from the worker's cache and still learns about a new deploy. The page and the worker are always one build: a page keeps the build it loaded with until it moves to the next one itself.

- K93. A half-filled cache. The worker fills its own cache `pikvm-shell-<build>` while it installs. A response that is missing, truncated, a redirect, a login page, or an HTML page standing in for a script (an expired session, a proxy's error page) fails the install, and the previous worker and cache keep serving; nothing partial is ever kept as the shell (a failed install deletes its cache, and a later try of the same build starts from nothing). The page it would have served is the build's `index.html`, and only when it holds the app's root element.
- K94. The shell is served for the wrong requests. Only a GET navigation to one of the server's page routes (`/app/`, `/app/kvm`, `/app/chat`, `/app/recordings` and below, `/app/settings` and below) gets the cached `index.html`; `/app/login`, `/app/logout`, `/app/auth*`, `/app/legacy/` (the KVM tab frames it), `/app` and any path the server does not serve as a page do not. The worker's list is one pattern that follows the server's `isAppPage`; adding a page route to one without the other is caught by the real-browser run, which asks every server route.
- K95. Something live or per-session is served from a cache, or kept in one: `/app/api`, `/app/chat/api`, `/app/chat/ws`, `/app/terminal`, `/app/legacy`, `/app/version.json`, sign-in and sign-out and OAuth pages, recording media (range requests), event streams, any non-GET and any other origin. Offline these fail, they are never stale. The worker answers from a cache only for what the build listed and for hashed files under `/app/assets/`; everything else is left to the browser, so a new route of ours is never cached by accident.
- K96. The cached UI pretends the host is there. Offline it opens at once, so the connection banner (K92) is what says the host does not answer, and the KVM, Chat and Recordings views say what they cannot do. Nothing in the cached page reads as live; a cached page never hides a failed request.
- K97. A signed-out or expired session is hidden by the cached shell. The shell holds no data, but it must not keep a signed-out person on an app screen once the host answers: the page asks `/app/version.json` when it starts and on every return, a 401 sends it to the sign-in page (with `next`), and the worker remembers that the person is signed out and asks the network first for the next page navigation (so no flash), showing the retry page, not the cached shell, when the host cannot be reached (a known sign-out is never hidden behind the cached app). A person not yet known to be signed out (the first visit after the session ended) can see the cached shell, which holds no data, for a moment until the page asks the host. The first 200 for an app page from the network clears that. The sign-in and sign-out pages and the sign-in POST are never served from a cache.
- K98. A new worker takes over a page running old code, or a page loses the files of its own build. The worker never calls `skipWaiting` on its own and never claims pages. It installs beside the old one and waits. It takes over only when no page is left, or when a page asks (`pikvm-apply`); that page then reloads into the new build. Until then every page is served from the cache of the build it loaded with. When another worker has already taken over, a page still on the old build still finds its lazy chunks in the old cache (hashed files are looked up in every build's cache, the build's own first), and an unhashed file (icon, manifest) is taken from the worker's own build.
- K99. Old caches are deleted too early or never. A cache of an old build is deleted when no page runs that build: on activation, and when a page starts, the worker asks every window client which build it runs and keeps the cache of each answer. A client that does not answer (frozen, still loading) keeps every cache for that round. While a newer (or older, after a rollback) worker is waiting or installing, no build's cache is deleted at all: the running worker cannot tell that worker's cache from an old build's, and the waiting worker's own activation does the clearing. The old runtime cache `pikvm-app-v1`, whatever else is not the shell or badge cache, and the old hashed files go with their build. The badge cache is never deleted. The worker keeps nothing in memory that it needs after the browser stops it.
- K100. An update is applied in the middle of use. The page applies a ready update by itself only at a quiet moment: when it has just started (nothing typed, no input yet), or when it comes back from being put away, and never while the host is recording, a text field holds typed text, or the last input was a moment ago. At any other moment a small toast with a Reload action says a new version is ready; it blocks nothing, appears once per build, and the update is taken at the next quiet moment if it is left alone.
- K101. A reload loop. A page reloads at most once per target build per tab session. If the page still runs the old build after that (the server keeps answering with it, the worker did not switch), it stays put, tells nobody twice and shows the build it runs in Settings > About.
- K102. A reload into the same cache. A page whose worker has not finished installing the new build must not reload for it: the reload would be served from the old shell. The page waits for the worker (`waiting`), and an app with no worker at all (the desktop app, plain http, private browsing, refused) takes the old way: a reload at a quiet moment, once per build.
- K103. `version.json` stops being the source of truth. It is never cached by the worker (a stale copy read as "a newer build" reloaded an offline app into nothing). Unknown (the host did not answer, not JSON, 401) is not "different": it starts no update. The worker's own build is baked into `sw.js` at build time so every deploy changes `sw.js`; `sw.js` stays public and revalidated.
- K104. A bad link makes the install a burden. The worker installs in the background, a few files at a time, one retry each; the grammars for code highlighting, the maths renderer and the second and third font formats are not in the precache (they are kept the first time they are used); a failed install is tried again at the next check and never blocks or slows the app that is running.
- K105. Two tabs. When one tab applies an update the other is moved onto the new worker while it runs the old build. It must not reload mid-use: it offers the update (K100) and keeps finding its chunks in the old cache (K98) until it does.
- K106. iOS standalone. Eviction of Cache Storage after a week without use leaves no cache: the navigation falls through to the network and then to the retrying offline page, and the worker fills the cache again on its next install check. The launch splash images are in the precache (iOS asks for them without the session cookie, so they are public paths). The standalone app has its own cookie jar and storage: its worker installs with the sign-in it has.
- K107. A page restored from the back/forward cache after a deploy runs an old build against a worker that has moved on. A restored page counts as a return (K100); its chunks that are gone from both the cache and the server are the one failure the page cannot avoid, so the check on return moves it forward quickly.
- K108. The precache list drifts from the build (a file renamed, a font added). The list is made from the build's own output (every emitted file except source maps and the optional chunks, and the public folder), so it cannot be edited by hand; the real-browser run opens every route offline after the first load and fails on any request that went to a host that was down.
- K114. A stalled install. A connection that opens and then never answers (a half-dead link, a proxy holding the request, a host that accepts and goes quiet) would leave the worker in `installing` forever: no `waiting` worker, so no update is offered, and the old worker keeps serving with no error shown. Every shell fetch has its own time limit per attempt (`FETCH_MS`, 60 seconds, long enough for one file on a slow link); a timed-out attempt is one failed attempt, retried once like any other (K104), and a failed install is deleted and tried again at the next check. The check: a stalled fetch ends the install within the limit, the worker is not left `installing`, the old build keeps running and its cache is untouched.
- K115. A refused file hangs the install. The host (or a sign-in proxy) refuses a shell file on purpose: a signed-out `/app/` is a redirect to the sign-in page, an asset is a 401, a missing file is a 404. That refusal is an answer, not a flaky connection, but the install retried it like a dropped connection: the retry's requests then never answered and never failed, so the worker stayed `installing` for minutes (the per-attempt limit K114 never ended them), with no `waiting` worker, no update offered and no error. Two fixes together: a refusal is not retried and its body is dropped so the connection is freed, and the first failed file ends the install by aborting the other lanes. The check: signed out during an install, the install ends within a few seconds, nothing is cached, the worker is not left `installing`, and the app that is running still draws.

## Video reconnection

The engine's video machine decides when WebRTC is retried and what the picture shows meanwhile (`packages/kvm-engine/src/video/FAILURE_MODES.md`, W6 to W19). This layer is the Janus wrapper (`janus-stream.ts`, with `rtc-health.ts` for the stats it reads) and the controller's side of it. Proof: `~/.cache/pikvm-e2e/rtc-resilience/`.

- K109. The wrapper reports each failure ONCE and has no retry of its own. A failure is: the Janus library not loading, the signalling socket lost or refused, a plugin error, an answer that cannot be made, ICE `failed`, the connection `failed` or `closed` (not by the wrapper), ICE `disconnected` for 3 s, silent media (K110), the Pi's hangup or detach. It tells the machine FIRST, so the picture is held while the video is still there, and only then tears the session down (peer connection, signalling socket, tracks, timers); a second failure from a session that has already failed says nothing. The old flat 5 s retry, the 2 s in-session retry after a plugin error and the `visibilitychange` re-ensure are gone: two timers over one session were how a failure could start two.
- K110. Silent media is read from the browser's own stats, once a second, only while the page is visible and only after media has flowed once. Dead means: the inbound video bytes, packets and frames, the inbound audio bytes and packets, AND the transport's bytes and responses received (selected candidate pair) have not moved for 4 s. The transport counters move on every STUN consent check, which the browser sends and the Pi answers whatever the picture does, so a static desktop (no frames, even no packets) is quiet but alive and is never restarted. A report with no transport counter, a failed `getStats`, or a missing field is "unknown": no verdict. The private `webrtcStuff.pc` Janus keeps is the only way to reach the connection; if it is gone there is nothing to read.
- K111. Audio and the microphone across reconnects. The speaker preference (`audioOn`) lives in the controller and is read when each session is created, so a session after a drop wants what the button says: off stays off, and the picture stays muted. A swap unmutes once (Chrome) or waits for the next touch (Safari, K38); a second drop and swap repeat exactly that, with no extra `play()` or unmute while the picture is already playing. The microphone is not carried: a session starts with it off (privacy, as on a fresh page load), so when a session ends while the microphone button said On, the button goes back to Off and says so, rather than showing On over a session that sends nothing. The camera is carried (K57).
- K112. The numbers for the adaptive phase are kept off the picture store. `controller.rtcStats` is its own small store: a plain object (`at`, `bitrateKbps`, `lossFraction`, `jitterMs`, `rttMs`, `fps`, `width`, `height`) refreshed every 2 s while a session plays and `null` otherwise. The picture store is read by the toolbar, dock, overlay and screen, so putting a sample in it would repaint them all every 2 s. Nothing is sent anywhere. Counters that go backwards (a new session) give no sample for that interval; a field the browser does not report is 0 (`rttMs` is `null` until a round trip is measured).
- K113. The chip words a lost video upgrade, and only that, as a suffix: "Live · reconnecting video" (amber) from the failure of a session that had played in this page until the next swap. It adds nothing when the signal already says "Reconnecting" or "Screen unavailable", it is not shown on a Pi that never had WebRTC, and it does not go to the connection banner: the banner is for the picture being gone, and here MJPEG is carrying it.
